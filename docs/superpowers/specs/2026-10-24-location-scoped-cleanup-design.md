# location の終了処理を、その location が受け持つ session だけに限る（`0.5.2-mageyuki.4`）

**状態：設計 rev4（designer-critical、2026-10-24）。rev5 の注記（2026-10-24、実装の最終 review の F1 による Controller の決定）を D3、D4、§5、§10 に足した。rev6 の注記（2026-10-24、再 review の RR1、RR2 による Controller の決定）で rev5 の (b) を置き換えた（D3、§5、§10）。** 範囲はユーザーが 2026-10-24 に承認した 3 点（下の「決まっている範囲」）。本書はその範囲の中の作り方を決める。rev2 は builder check を反映した（§8）。rev3 は plan-reviewer-critical の指摘 B1、B2、N1、N2 を直した（§9）。rev4 は再 review の 2 つの blocking を直した（§10）：受け持ちを、OpenCode が出す「session の今の location」（`session.moved`）にいる instance だけが取れるようにした。親への link などの 1 回きりの事実は、受け持ちに関係なく記録する。実装・commit・publish・config の変更・再起動はどれも行っていない。調査は read-only（fork の source、upstream の枝、OpenCode 2.1.4 の bundle の該当箇所、`@opencode/schema` の型、local の `opencode.log` と `opencode.db` の件数、Issue #223 の debugger の報告）。

## 0. 先に読むこと

- **現在の判断：** OpenCode 2 の plugin instance（location ごとに 1 つ）が、process で共有している client の中で「自分が今受け持っている session」を登録する（hold）。受け持ちは、session の今の location（`session.moved` で記録）にいる、生きている instance だけが取れる。event で session の状態を変えてよいのは受け持つ instance だけで、破棄の後の callback と、受け持っていない instance の event は何もしない。親への link などの 1 回きりの事実は、受け持ちに関係なく記録する。instance の終了処理は、自分が受け持っている session だけを終える・片付ける。他の session の observation と、すべての session の版の履歴と親の session への link には触れない。版の履歴が無い・消えた窓には `agentsMdStatus=unavailable` を付け、全体の reset（`clearTraceState`）では履歴の coverage を無効にする。
- **なぜ：** Issue #223 の D8（task の 90% 以上に release、空のものはすべて status で説明）を満たしていない。160 件中 38 件が空で、そのうち 32 件はこの不具合（location の破棄が process 全体の状態を消す）による（§2 E1）。
- **次の actor：** Controller が rev4 の修正を直接確かめる（§10）。その後、計画（`writing-plans`）か実装。
- **ユーザーに残る行為（設計の問いではない）：** publish の承認、fork と config の PR の merge（host の規則どおり）、再起動の時刻。設計についてユーザーに聞くことは無い（§7）。

### 決まっている範囲（ユーザー承認、2026-10-24）

1. location の cleanup は、共有 client の中の他の session の active な observation と、版の履歴を終えない・消さない（主な修正）。
2. 窓の履歴が無い・消えたときは説明の status（例：`unavailable`）を付け、その窓の coverage を無効にする。説明の無い空と、誤った帰属を無くす。
3. task の emit の時点で generation が未確定の 5 件は、今回は受け入れる限界（`onStart` の時点の再設計はしない）。

範囲外：evaluation-grains の変更、`promptVersions` の option の schema の変更、upstream への提案。

## 1. 目的・非目的・反目標

**目的。** 複数の location（directory、worktree）を持つ OpenCode server で、1 つの location が破棄されても、他の location の session の trace（turn、generation、tool）と、task・turn の版の帰属が壊れないようにする。D8 の受け入れを満たす。

**非目的。**

- task の帰属の時点（`onStart` で 1 回、待たない）を変えること。pending の 5 件は限界のまま。
- OpenCode 1 の entry（`src/v1.ts`）の終了処理を変えること（§3 D7）。
- plugin を reload したときに nesting を保つこと（upstream main の `c7f3a20` の storage 方式）。
- upstream に提案すること。

**反目標（動いても失敗とみなすもの）。**

- 他の location の session の observation を終えること、版の履歴を消すこと。
- 終了処理の範囲を狭めた結果、放置された observation が永久に開いたまま（export されない）になること、session ごとの状態が process の寿命まで解放されないこと。
- 誤った版を付けること。部分的な履歴から値を作ること。
- tracer provider を止めること、instance の破棄の後に export が止まること。
- span processor の数・型、option の schema、metadata の key と値の種類、`promptVersionsSchema` が変わること。
- 共有 client が別の build のものでも、hook が例外を投げるようになること。

## 3. 決定

### D1. 持ち主の区分

| もの                                                                                             | 持ち主                                      | 終わり方                                                                                        |
| ------------------------------------------------------------------------------------------------ | ------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| tracer provider、span processor、export の queue                                                 | process（共有 client）                      | instance の破棄では止めない。flush だけ（今のまま。E7 と同じ契約）                              |
| prompt link の cache、options の持ち主の規則                                                     | process                                     | 今のまま                                                                                        |
| 版の履歴（`SessionVersionHistory`）                                                              | process                                     | session の削除（`session.deleted`）と LRU でだけ減る。instance の破棄では消さない               |

| session の今の location（`session.moved` の行き先。rev4）                                        | process                                     | session の削除と、上限（2000 件、古い順）でだけ減る。instance の破棄では消さない（D3 の F、D5） |

trace state を instance ごとに分けず、process で共有したままにする理由：session は location をまたいで続く（location の再作成、`session.moved`）。親と子の session の nesting も共有の map で引いている。共有をやめると、それが切れる（D2 の案 D）。

### D3. 受け持ち（hold）の規則（rev3、rev4）

**原則（rev4）：受け持ちは、session の今の location にいる、生きている instance だけが取れる。event で session の状態を変えてよいのは、その session を受け持つ instance だけ。** 古い location の instance に遅れて届いた callback は、受け持ちを取れず、受け持っていない instance の event は何もしない。順序をそろえる仕組みは持たず、OpenCode が出す「session の今の location」（`session.moved`）という事実だけを使う。

- 共有 client に「session → 受け持ちの instance」の表を置く。値は instance ごとに 1 つの token（setup の中で作るもの）で、token はその instance の location（`ctx.location` の `directory` と `workspaceID`。E10）を持つ。2 つの location は、`directory` と `workspaceID` の両方が等しいとき同じとみなす。`ctx.location` が無い instance（テストの mock など）は、自分の location が分からないので、下の「今の location と同じか」の比較を常に満たすものとして扱う。
- **R1（破棄の後は何もしない）：** instance は、cleanup の最初（`abort.abort()` の前）に自分の `disposed` の印を立てる。印が立った後の hook と event は、入口で何もせずに戻る。受け持ちも取らず、client も呼ばない。OpenCode の `PluginHooks.trigger` は、先に取り出した callback の配列を回すので（`register` の `dispose` は登録簿から外すだけ）、破棄した instance の hook が後で呼ばれることがある（B2）。それを入口で止める。
- **rev5（2026-10-24、reviewer-critical の F1。Controller が決定）：** 次の 2 つの例外・回復を足した。
  - **(a) R1 の例外：** `disposed` の印の後も、event の loop が終わるまでに届いた F の事実（`session.created` の親への link、`session.moved`、`session.deleted`）は処理する。どれも turn や observation を作らない。印の後の hook と run の event は、今どおり何もしない。印の後の instance は `session.moved` で今の location を記録し、行き先と違う受け持ちを外すが、自分では受け持たない。
  - **(b) 確かめられない記録からの回復（R2、R3。rev6 で置き換えた。下の rev6 を見よ）：** 記録された今の location に、生きている（印の立っていない）instance が 1 つも無いとき、その記録は誰にも確かめられない。そのときは、誰も受け持っていない session を、別の location の instance も受け持てる。記録された location に生きている instance があれば、別の location の instance は今どおり受け持てない（B1 の保護は残す）。生きている instance は、受け持ちの表を開いた時から、cleanup の最初（印を立てる時）までのもの。location が分からない instance は、どの記録も確かめない。
  - 理由：location の記録が `/a` で、`/b` への移動が A に届いたとき、A の event の loop が `forceFlush` を待っている間に A の cleanup が始まると、移動は捨てられ、記録は `/a` のまま残る（解放は記録を残す）。後で作られた B（`session.moved` を受け取っていない）は受け持てず、B の run の event は捨てられ、turn は終わらない。一時的ではなく、ずっと続く。(a) で、loop の中に残っていた移動は記録される。(b) で、移動が loop に届かずに失われても回復する。
- **rev6（2026-10-24、再 review の RR1、RR2。Controller が決定。rev5 の (b) を置き換える）：**
  - **回復の条件は「その session に今の受け持ちが無い」こと**（「記録された location に生きている instance が無い」ではない）。
  - **R2（hook）：** 受け持ちが無ければ、どの location の instance も受け持つ。受け持ちがあれば、記録された今の location が無いか自分と同じときだけ、自分に移す（B1 の保護は変えない）。
  - **R3（run の event）：** 自分が受け持っていれば処理する。受け持ちが無ければ受け持って処理する（どの location でも）。それ以外は何もしない。
  - 破棄の印の後の instance は受け持たない。rev5 の生きている instance の集合は無くした（setup が途中で失敗した instance が回復を止めるリスクも無くなった）。印は instance の中に持つ（`close()`）。
  - **RR2：** 印の後の instance が、自分の location を行き先とする `session.moved` を処理したときも、行き先と違う location の受け持ちを外す（自分では受け持たない）。
  - 理由：受け持ちが無いのは、どの生きている instance もその session を trace していないということなので、古い location の instance が受け持っても、他の instance の turn を終えることは無い。行き先の instance は、最初の hook で R2 によって取り返す（記録された location が自分と同じ）か、F の `session.moved` で受け持つ。rev5 の条件では、移動が失われた後に古い location が作り直される（E6 のふつうの順序）と、作り直された instance がいるために行き先の instance が受け持てず、run の event が捨てられ、turn が終わらなかった（RR1）。
- **F（session の事実は、受け持ちに関係なく記録する。rev4）：** 次の event は、生きている instance なら、受け持っていなくても処理する。どれも、active な observation を終えたり変えたりしない。
  - `session.created`：親への link（`parentID` があるとき）。1 回しか出ないので、捨てると取り戻せない（rev4 の指摘 2）。
  - `session.moved`：その session の**今の location**（`data.location`。E10）。同じ session について、前に記録したものより新しい event（`durable.seq` が大きい）だけを記録する。記録した instance は、受け持ちを次のように直す：自分の location が行き先なら、自分が受け持つ。そうでなければ、今の受け持ちの location が行き先と違うときに、受け持ちを外す。
  - `session.deleted`：R4。
  - `v2.ts` が扱う、ほかの 1 回きりの事実は無い（ほかの event は run ごとに何度も出るもので、R3 に従う）。
- **R2（hook は記録を書き、受け持ちは今の location でだけ移す）：** hook（`session.prompt`、`session.context`、`tool.execute.before`、`tool.execute.after`。`input.sessionID`）は、client の処理を必ず行う。hook の内容（prompt、context、tool の入出力）は、遅れて呼ばれても本物だから。そのうえで、その session の今の location が記録されていないか、自分の location と同じときだけ、自分を受け持ちにする（他の instance が持っていても移す）。記録された今の location が自分と違えば、受け持ちは変えない。
- **R3（event は受け持つ instance だけが処理する）：** `v2.ts` が処理する event のうち F 以外（`session.step.started`、`session.text.ended`、`session.reasoning.ended`、`session.step.ended`、`session.step.failed`、`session.retry.scheduled`、`session.execution.failed`、`session.execution.succeeded`、`session.execution.interrupted`。`event.data.sessionID`）は、自分がその session を持っているときか、誰も持っておらず今の location が記録されていないか自分と同じとき（このときは受け持つ）だけ処理する。それ以外は丸ごと何もしない（client を呼ばない）。
  - 理由（rev3 の B1）：event の loop は `forceFlush` を待つ（`src/v2.ts` L276、L291）ので、古い location の instance A には、session が B に移った後でも古い event が遅れて届き得る。R3 によって、その event は B の turn を終えず、受け持ちも取り返さない。
  - 理由（rev4 の指摘 1）：`Session.prompt` は取ってきた session の object の location で `SessionPrompt.prepare` を動かし、`PluginHooks.trigger` は callback を順に待つ。だから、生きている A の hook が、session が B に移った後に遅れて呼ばれることがある。R2 では、`session.moved` が記録された後の A の hook は受け持ちを取れない。記録の前に A が受け持っても、`session.moved` を記録した時点で外れる（F）。
  - **B の event は落ちない：** OpenCode は `session.moved` を移動の時に出し、B での処理の event はその後に出る。B の event の列は 1 本で順番どおりなので、B は自分の最初の移動後の event より先に `session.moved` を処理し、F で受け持つ。移動の時に B の instance がまだ無かった（後で作られた）場合は、B は `session.moved` を受け取らないが、A が記録して自分の受け持ちを外すので、B は「誰も持っておらず、今の location が自分と同じ」session として受け持つ。
  - A がまだ受け持っている間に届いた A の event は、移る前の A の run の event なので、そのまま処理してよい。B が受け持った後に届いた、移る前の A の event は捨てる（下の「移る時の取りこぼし」）。
- **R4（削除）：** `session.deleted` は、生きている instance なら、受け持ちに関係なくその session を全部片付ける（履歴、親への link、今の location も消す）。受け持ちも消す（D5）。session が無くなった後に続く event は無いので、遅れても害が無い。
- `session.forked` は受け持ちに使わない。
- 表の大きさは、生きている instance が受け持つ session の数まで（解放と削除で消える）。受け持つ操作は `Map` の参照と更新だけで、hot path で待つものは無い。
- **v2.ts の callback が途中で待たないこと：** hook の callback は同期的で、event の処理も client を呼んだ後に `forceFlush` を待つだけ。だから、R1〜R3 と F の判定と client の呼び出しの間に、他の instance の処理や cleanup が割り込むことは無い（JavaScript の実行は 1 本）。cleanup は event の loop が終わるのを待ってから解放する（D4）。
- **規則が閉じていることの確認（rev4）：** 受け持ちを取れるのは R2、R3、F の 3 か所だけで、どれも「今の location が記録されていないか、自分と同じ」を条件にする。外れるのは F（行き先と違う）、解放、削除だけ。したがって、`session.moved` が記録された後は、行き先の location の instance しか受け持てない。process の間に動いていない session では、すべての callback がその session のただ 1 つの location から来る（E5）。動いたがまだ記録されていない間に古い A が受け持っても、記録した時点で直る（R3 の理由、rev4 の指摘 1）。
- **移る時の取りこぼし（受け入れる）：** 次の 2 つの場合だけ、event が R3 で捨てられる（§5）。
  - 実行中の session がある location が作り直されるとき（config の変更など）：破棄の途中の instance がまだ持っている間に、作り直された instance に届いた event。次の hook か、古い instance の解放で終わる。idle で破棄される location（E4）では起きない。
  - session が移ったとき：B が受け持った後に A に遅れて届いた、移る前の A の run の event（その run の最後の step の出力など）。移動は少ない（E10：31 日で 81 回、debugger の期間では 1 回）。

**前提（rev2。E5 で確かめた事実）と、崩れたときの規則：**

- OpenCode 2.1.4 では、ある session の hook（`session.prompt`、`session.context`、`tool.execute.before`／`after`）も、`v2.ts` が処理する event も、**その session の location の instance にだけ届く**（`session.moved` は移動前と移動後の両方に届く。F で使う）。ただし、届く**時刻**は遅れ得る：event の loop は待ち、hook も、取ってきた session の object の location で、callback を順に待ちながら呼ばれる（rev4 の指摘 1）。だから、届く先が正しいことだけには頼らず、受け持ちは「記録された今の location」でも絞る（R2、R3、F）。計画に、この確認のための関門は要らない。
- **再起動の時の binary が v2.1.4 でなければ**（OpenCode が更新されていたら）、有効化の前に Controller が E5 と同じ read-only の確認をやり直す。確かめる箇所：`Py.make("location")` の service に `@opencode/PluginHooks` が入っていること、`SessionPrompt.prepare` が `Hu.provide(session)` の中で `trigger("session","prompt")` を呼ぶこと、`@opencode/Tool` と `@opencode/SessionModelRequest` が location の service で `ZT` を使うこと、bus の `subscribe` が `Location.Service` で絞ること、`Plugin.Event.makeStreams` が setup の時の runtime で stream を回すこと。`session.moved` が plugin に配られる event の集合（`DZ`）に入っていて、`data.location`（行き先）と `durable.seq` を持つこと。plugin の `ctx.location` が `directory` と `workspaceID` を持つこと（E10）。
- **崩れていたとき**（1 つの session の hook か、処理する event が、複数の location の instance に届く）：builder も Controller も、その場で別の方式（event だけで受け持つ、hook の入力で location を絞る、など）に切り替えない。設計に戻す。理由：hook の入力には location が無いので、hook の側では絞れない。event だけで受け持つ案では、hook が作った状態（`session.prompt` の turn、`session.context` の snapshot）に、最初の event までの間、持ち主がいない。どの案で足りるかは、破れ方（hook だけか、event もか）によるので、その時点の事実で設計し直す。
- live では D10 の 3 が、この前提の破れを検出する（OpenCode の更新の後に再実行する）。

### D4. 終了処理（解放）

instance の cleanup は次の順にする。

1. `disposed` の印を立てる（R1。以後、この instance の hook と run の event は何もしない。rev5：F の事実は loop が終わるまで処理し、この instance は受け持ちの表で「生きている」ものから外れる）。
2. `abort.abort()`、hook の登録の解除、event の loop の終了を待つ（今のまま）。
3. **自分が今受け持っている session だけ**について、次を同期的に行う。
   1. `endActiveToolObservations(s)` → `endActiveGenerationSteps(s)` → `endActiveTurnObservations(s)`（今の `session.execution.succeeded` の処理と同じ。G5／T2 の経路なので、版の判定と turn の stamp もここで行われ、未確定の記録も残らない）。
   2. その session の trace state を片付ける（D5）。**版の履歴と、その session の親への link は残す。**
   3. 受け持ちを消す。
4. `forceFlush`（今のまま）。`clearTraceState()` は呼ばない。provider は止めない。

- 受け持ちが他の instance に移った session は、何もしない（その instance が続ける）。
- 解放の後に、この instance の hook が呼ばれても、R1 で何もしない。だから、解放の後に新しい受け持ちや、終わらない turn は生まれない（B2）。
- 印を立てた後、event の loop が終わるまでに届いた event も処理しない。その event が run の終わりだった場合、その run の observation は 3 の解放で終わる（終わりの時刻が、event の時刻ではなく解放の時刻になる）。
- 放置された observation（終わりの event が来なかった turn など）は、受け持っていた instance の破棄で今どおり終わり、export される。
- 履歴を残す理由：履歴は「確定した版と時刻」という事実で、location が破棄されても正しい。上限（2000 session の LRU、session ごとの区間の上限）がある。破棄された location の session が作り直された location で続くと、窓が破棄をまたいでも正しく帰属できる（E1 の 3 件）。

### D5. session ごとの片付け（記憶の扱いを今と同じ程度に保つ）

今は、どこかの location の破棄のたびに全消去が走り、結果として全 session の状態が回収されている（E8）。A ではそれが無くなるので、解放と削除で、その session の分を確実に回収する。

- **片付ける関数（新しい。名前は builder）：** `forgetSession(sessionID, { keepSessionFacts })`。返った後、client はその session に属する次のものを持たない。`keepSessionFacts` のときは「session の事実」（版の履歴、その session の親への link、その session の今の location。rev4）だけを残す。
  - session で引く map：今の `clearSessionTraceState` が消すもの全部と、`turnVersionSummaries` のその session の分。
  - `sessionParentIds`：**key がその session の entry**（その session を子とする「子 → 親」の link）。`keepSessionFacts` のときは残す。値がその session の entry（その session を親とする子の link）は消さない。それは子の事実で、子の削除か上限で消える。
  - message、call、event の ID で引く map と set のうち、**その session のために足した entry**：`tracedMessageIds`、`tracedGenerationIds`（assistant の message ID と、失敗した step の event ID）、`tracedEventIds`、`generationSpansByMessageId`、`activeGenerationStepsByMessageId`、`turnObservationsByMessageId`、`assistantParts`、`toolMessageIdsByCallId`、`activeToolObservations`、`finalizedToolCallIds`、`tracedReasoningIds`。
  - その session の今の location（D3 の F）：`keepSessionFacts` のときは残す。
  - 受け持ち（D3）。
- **ID で引く entry を session に結びつける方法：** entry を足すすべての箇所で、その session の索引（session → その session のために足した ID）にも足す。足す箇所では session が分かっている（`input.sessionID`、`part.sessionID`、`observation.sessionID`）。索引の形は builder に任せる。
- **使い分け：**
  - 解放（D4）：`forgetSession(s, { keepSessionFacts: true })`。
  - v2 の `session.deleted`：`forgetSession(s, { keepSessionFacts: false })`（今の `clearSessionTraceState` と同じく履歴も消す。加えて ID の entry、key がその session の `sessionParentIds`、その session の今の location も回収する）。
  - `clearSessionTraceState`（v1 が `session.idle` で使う）は、**今の意味のまま**にする。v1 は message の更新の event から span を作るので、idle の後に同じ message の event が届くと、重複を防ぐ set を消した場合に span が二重になり得る（確かめていない。v1 の挙動を変えないための判断）。索引のその session の entry と受け持ちだけは消す（帳簿だけで、v1 の挙動は変えない）。
  - `clearTraceState`（全体の reset。v2 からは呼ばなくなる）は今の意味のまま。索引と受け持ちも消し、履歴の消去は coverage を無効にする（D6 の H1）。
- 回収の時点は、その location が idle で破棄される時（60 分）か、session の削除か、OpenCode の終了。これは upstream を 1 つの location で使う場合と同じ。

**親の session への link を解放で残す理由と、その上限（rev2、builder check の Q2）：**

- `sessionParentIds` は、子の session の `session.created`（`parentID` つき）で 1 回だけ記録される。`session.created` は作成の時の event なので、子の session が後で続くとき（親が subagent の session を `sessionID` で再開するなど。v2.1.4 の subagent の tool は `sessionID` の入力を受け付ける）には出ない。
- 解放で消すと、作り直された location で子の session が続いたとき、子の turn は親の span の下に入らない。`getSessionParentSpan` が親を引けないので、子の turn は `langfuse.internal.is_app_root=true` の root の trace になり、metadata の `parentSessionID` も空になる。root turn は Helpfulness の母集団なので、母集団が変わる（反目標）。今の不具合でも、どこかの破棄のたびに同じことが起きている。
- link は「この session はあの session の子」という事実で、location の破棄で変わらない。版の履歴と同じ扱いにする。
- **上限：** `sessionParentIds` は最大 2000 件（版の履歴の session の上限と同じ）。超えたら、最も古く記録した entry から消す。entry 1 件は ID の文字列 2 つで小さい。上限で消えた子の session が後で続くと、子の turn は root になる（§5）。
- **残しても nesting が保たれる理由：** 子の session が続くのは、親がまた動いているとき（作り直された location で、親の generation が active）。`getSessionParentSpan` は、親の今の active な generation か turn の span を、共有の map から引く。親の側の古い状態は要らない。
- `clearSessionTraceState`（v1）は、今どおり `sessionParentIds` を消さない。`clearTraceState` は今どおり全部消す（今の location の記録も消す）。
- **今の location の記録（rev4）も同じ扱い：** 解放では残し、削除で消す。上限は 2000 件、古い順（移動は 31 日で 81 回なので、ふつうは届かない。E10）。上限で消えた session は「記録されていない」に戻り、R2、R3 は記録が無いときの規則で動く。

### D6. 履歴が無い・消えた窓の status

- **H1：全体の reset は coverage を無効にする。** `SessionVersionHistory.clear()` は `coverageCompleteSinceMs` を `max(今の値, now)` にする。reset より前から始まる窓は `unavailable`。
  - 理由：reset の後に新しく確定した値だけで、reset をまたぐ窓の値を作ると誤る。例：窓 `[5, 40]`、`@7` が t=10 に確定、t=20 に reset、`@8` が t=30 に確定 → 正しくは `:mixed` だが、今の実装は `@8` を返す。
- **H2：`summarize()` は `none` を返さない。** 窓の中にも、窓の前にも確定した値が無いとき（session の記録が無い場合を含む）は `unavailable` を返す。したがって、`promptVersions` が有効なら、`session.id` を持つ span（generation と turn 以外）と、有効な間に始まった turn は、値か `agentsMdStatus=unavailable` のどちらかを必ず持つ。
  - 理由：「記録が無い」は「その前に版が無かった」を証明しない（再起動の前から続く session、LRU で捨てた session、reset、削除の後に届いた span）。窓の契約の「窓の前で最後に確定した値」が決められないので、不明として扱う。
  - session の削除（`drop`）には墓標を持たない。削除の後に届いた span は、記録が無いので H2 で `unavailable` になる。
- **status の値：** 既存の `unavailable` を使う（`#223` の D4 の列挙のまま。`promptVersionsSchema` は `"1"` のまま）。理由の区別のために新しい値（例：`no_history`）を足す案は、列挙と下流の集計の手順を変えるので採らない。
- **結果として変わること：** 新しい session の最初の generation より前の span（最初の `opencode.message.user` の event など）と、確定した generation が 1 つも無い turn にも、`agentsMdStatus=unavailable` が付く。今は何も付かない。どちらも release は付かないので、release ごとの集計は変わらない。
- generation の span（G1〜G5）の付け方は変えない。

### D7. 互換性

- **共有 client が別の build のもの（受け持ちの API が無い）：** instance は受け持ちを取らず、cleanup は flush だけ、`session.deleted` は今どおり `clearSessionTraceState`。API の有無は、prompt link の marker と同じく、実行時に確かめる（hook が例外を投げないこと）。
- **この build の client を古い build（`.3`、upstream）の instance が共有：** その instance の破棄は今どおり全消去する。H1 によって、影響を受けた窓は `unavailable`（説明つき）になる。
- **span processor：** 数と型を変えない（evaluation-grains の gate、3〜5 個）。

### D10. live の受け入れ（再起動の後、read-only）

期間と分母は `#223` の D8 と同じ（再起動の 5 分後から 24 時間か、root turn が 50 件に達するまでの長い方）。

1. task と root turn のそれぞれで、`langfuse.release` が空でないものが 90% 以上。
2. release が空の task と root turn は、**すべて** `agentsMdStatus` を持つ（H2 によって、status の無い空は 0 件のはず）。
3. **主な修正の確認（rev3、N2 で書き直した）：** 時刻が近いことは候補を選ぶのにだけ使い、合否は「turn の span が、その turn の run より先に終わったか」という因果の印で決める。
   - **印（OpenCode の記録で判定する）：** OpenCode の DB（`~/.local/share/opencode/opencode.db`、read-only）の `session_message` には、run の終わりに `type = 'idle'` の行（`outcome` と `time.created` つき）が、新しい prompt に `type = 'user'` の行が入る。turn は run の終わり（`session.execution.succeeded`／`interrupted`／`failed`）か、次の prompt で正常に終わる。そこで、root turn（開始 S、終わり T）について、同じ session の行を見る。**正常**：S の後の最初の `idle` の行が T + 2 秒より前にある、または S と T + 2 秒の間に次の `user` の行がある（run の途中の prompt で終わった場合）。**強制終了**：どちらも無い（turn の span が終わった後も、その run が続いていた）。2 秒は、event の作成から plugin の処理までの遅れの余裕。
   - **印が測れることを先に確かめる：** 修正の前の期間（debugger の期間、2026-10-21 14:48Z〜2026-10-24 08:26Z）に、同じ印を当てはめる。eviction の直後に終わった、他の directory の 29 件のうち大部分が「強制終了」になり、eviction に近くない root turn では「強制終了」がほとんど出ないこと。そうならなければ、この印は使えないので、3 は「未確認」として記録し、1、2、4 で判断する。
   - **候補：** 期間内の `location services evicted` のそれぞれについて、その時刻に開いていた root turn（開始 < eviction < 終了）のうち、破棄された directory ではない session のもの（directory は `session_v2` で引く）。
   - **合否：** 候補のうち「強制終了」が 0 件。あわせて、期間内の root turn 全体の「強制終了」の件数を、修正の前の期間の件数と並べて報告する（eviction 以外の原因で早く終わる turn も見えるようにする）。
   - 期間内に候補のある eviction が 1 つも無ければ、3 は「未確認」として記録し、期間を延ばす。
4. debugger の分類をもう一度当てはめ、「location の破棄で履歴が消えた」は 0 件。残る空は pending（受け入れた限界）か、再起動をまたぐ窓だけ。
5. evaluation-grains の route が `ok`、task の件数が再起動の前と同じ程度。
6. **観察（合否ではない）：** OpenCode server の RSS を、再起動の直後と 24 時間後に記録する（D5 の回収の時点の変化を見るため。§5）。

## 5. リスクと限界

| リスク                                                                               | 扱い                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

4. 回収の範囲を、message、call、event の ID の entry まで広げる（D5）。v1 の `clearSessionTraceState` の意味は変えない。
5. 履歴が無い窓は `none` をやめて `unavailable`（H2）。新しい status の値は足さない。全体の reset は coverage を無効にする（H1）。
6. 共有 client が別の build のものなら、受け持ちを取らず flush だけ。
7. v1 は変えない。
8. （rev3）D10 の 3 は、時刻の近さで候補を選び、OpenCode の `session_message` の `idle`／`user` の行で「run より先に終わった turn」を判定する。印は、修正の前の期間で使えることを先に確かめる。RSS は観察（合否ではない）。
9. （rev2）解放では、その session の親への link（`sessionParentIds` の key がその session の entry）を版の履歴と同じく残す。削除で消すのは key がその session の entry だけ。上限は 2000 件、古い順。
